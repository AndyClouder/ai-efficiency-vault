# FDE 模式（Forward/Field Deployed Engineer）

> 用户（安迪）的核心职业身份之一，本页是库内高优先级概念页。

## 当前综合结论

FDE（Forward Deployed Engineer / Field Deployment Engineer，前沿部署工程师）是 AI 时代催生的一种交付角色，介于咨询与外包之间却本质不同。三者共享同一母问题——"客户需要的东西，我手头没有现成的"——但对"为什么没有"的前提假设不同，因此核心输出截然不同：

- **咨询**交付**认知**（洞察、框架、路线图），假设"知识可被传授"，反馈去向是客户
- **外包**交付**产能**（功能、代码、系统），假设"知识可写进需求文档"，反馈去向是客户
- **FDE**交付**转化**（代码 + 认知 + 产品洞察），假设"知识只能在行动中涌现"，**反馈去向是自己的产品团队**——这是 FDE 与"驻场外包"的本质分水岭

FDE 的核心价值在于**反馈闭环 + 复利效应**：把不可定义的问题在现场定义出来，再把现场经验沉淀成产品能力反哺所有客户。"没有反馈闭环的 FDE 就是外包；没有落地承诺的 FDE 就是咨询。" AI 时代（尤其 Claude Code 这类工具）急剧降低了"探索"与"执行"的切换成本，使一个 FDE 能包揽过去三角色接力的事——但这只在"把现场经验带回产品团队"的前提下成立，否则只是更快的在外包。

## 关键事实与观点

### 第一性原理：三种角色的前提假设
- 咨询假设：客户有需求但不知道需求长什么样 → 帮他想清楚，交付认知（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）
- 外包假设：客户知道需求但没时间/能力做 → 帮他造出来，交付产能（来源：同上）
- FDE 假设：客户连需求都说不清，因为问题本身在认知之外 → 到现场一起定义问题再造方案，交付转化（来源：同上）

### 元认知视角：三种知识生成模型
- 咨询 = "知识转移"模型，核心能力是抽象能力（套框架）（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）
- 外包 = "知识执行"模型，核心能力是工程能力（翻译确定性需求）（来源：同上）
- FDE = "知识涌现"模型，核心能力是**双重翻译能力**（业务感知↔技术方案、现场经验↔产品需求）（来源：同上）
- 一句话概括："咨询相信知识可被传授；外包相信知识可写进文档；FDE 相信知识只能在行动中涌现。"（来源：同上）

### 分水岭标尺：三个维度
- 价值交付物：PPT（咨询）/ 代码+交接文档（外包）/ 代码+产品改进提案+客户持续在用（FDE）
- 互动方向：客户（咨询/外包）/ 自己的产品团队（FDE）
- 复利效应：无（咨询/外包）/ 有飞轮（FDE）
- **最关键分水岭 = "反馈去向"**：FDE 反馈给自己的产品团队，这是与驻场开发的本质区别（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）

### 实用判断框架（三问）
- Q1 客户知道要什么吗？知道且有文档→外包；模糊可访谈→咨询；完全无法定义需摸索→FDE
- Q2 下一个客户怎么办？不关心→外包；写报告→咨询；沉淀进产品→FDE
- Q3 交付物是什么？PPT→咨询；代码+交接文档→外包；代码+产品改进+持续在用→FDE
（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）

### AI 时代如何模糊边界
- AI 让"探索"与"执行"切换成本急剧降低：FDE 用 Claude Code 半天搭原型→原需反复开会的需求定义阶段被压缩
- **关键警示**："如果你以'外包'心态进客户现场，AI 不会把你变成 FDE，你只是比原来写代码更快的外包。真正的分水岭不是'会不会用 AI'，而是'你把现场经验带回了哪里'。"（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）

### 价值本质
- "咨询赚的是认知的钱。外包赚的是效率的钱。FDE 赚的是复利的钱。"（来源：[[2026-06-02-FDE-vs-咨询-vs-外包：三个角色的分水岭到底在哪]]，2026-06-02）
