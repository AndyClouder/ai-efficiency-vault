# 网络调研

> 主动出去搜，综合好再落盘。产出物 = 一批带源 URL 的结构化 md，躺在 `0_Inbox/搜索/` 下，等「知识分类」「知识关联」等下游 skill 接手。

---

## 触发条件

- 用户说："调研 X" "调研一下 X" "搜一下 X" "搜索 X" "查一下 X 的最新动态" "查 X 最近怎么样" "研究一下 X" "找找 X 的资料"
- 用户键入：`/调研 [主题]`、`/搜索 [主题]`
- 用户给出一个**信息需求**（而非一条具体 URL）——例如"最近字节有什么组织变动""特斯拉高管层最近有谁走了"，这是「网络调研」的活儿，不是「知识入库」的活儿

**与「知识入库」的边界**：用户直接粘 URL/文本 → 走「知识入库」；用户问"X 最近怎么样/帮我查 X" → 走「网络调研」。

---

## 工作流程

### 第 0 步：开始前告知预算

在动手搜索前，明确告知用户本次将消耗的网络额度（透明，避免无意识烧额度）：

> 即将开始调研「{主题}」。计划：2 轮搜索 × 约 6 个信源，预计发起 10-15 次 WebSearch + WebFetch。开始？

得到确认（或用户已经明确要查时直接进入）。

### 第 1 步：规范化主题

1. 从用户输入中提取**主题词**，必要时向用户确认理解是否准确
2. **主题名做文件名安全化**：去掉 `/ \ : * ? " < > |` 等非法字符，长度控制在 4-20 字
   - 例："字节跳动 2026 年组织架构调整（含抖音/剪映整合）" → 主题名 `字节跳动组织调整`
3. 确定主题的 3-5 个核心标签（中文，不要"AI"这种太泛的词，用"AI效能""组织架构"这种更具体的）

### 第 2 步：拆解搜索角度

把主题拆成 **3-4 个互不重叠的搜索角度**。例如主题"字节跳动组织调整"：

- 角度 A：字节跳动近期组织架构调整事件本身
- 角度 B：涉及的关键人物变动（谁上任/卸任）
- 角度 C：涉及的部门/业务线调整
- 角度 D：业内评论与分析

### 第 3 步：Round 1 广搜

对每个角度：

1. `WebSearch` 1-2 次查询（中英文都试，技术类偏英文，公司动态偏中文）
2. 收集候选 URL，**过滤**掉：
   - 不是 `http(s)://` 的（拒绝 `file:` `javascript:` `data:`）
   - 内网地址（`10.x` / `172.16-31.x` / `192.168.x` / `localhost` / `127.0.0.1`）
   - 搜索结果里没出现过的域名（不跟着重定向乱跑）
3. 从所有候选中选 **top 6 个** 最相关、最权威的 URL（权威度优先级见下方"来源偏好"）

### 第 4 步：逐个 WebFetch 抓取

对选中的 6 个 URL，逐个 `WebFetch` 抓正文：

- 提取：标题、作者、发布日期、关键论点、涉及实体（人/组织/产品）
- **失败处理**：抓取失败的 URL 记下 URL + 原因（超时/4xx/5xx/内容过大/被清洗为空），不中断流程，最后写进综合页的 Open Questions
- **截断**：单个信源正文超 ~50KB 的，截断保留关键段落

### 第 5 步：Round 2 补缺（关键）

横向看 Round 1 的 6 个信源，识别：

- **矛盾**：信源 A 说 X，信源 B 说 Y，但没人能定论
- **缺口**：关键信息缺失（比如不知道新任 CEO 是谁、不知道调整生效时间）

针对每个矛盾/缺口，发起最多 **3 次**定向 `WebSearch` + `WebFetch` 补齐。

> 触发停止：所有主要问题都有答案，或补到 3 次上限，进入下一步。

### 第 6 步：建目录

在 `0_Inbox/搜索/` 下创建：

```
0_Inbox/搜索/YYYY-MM-DD/主题名/
```

- `YYYY-MM-DD`：今天日期
- `主题名`：第 1 步规范化的主题名

### 第 7 步：写每个信源 md

每个有效抓取到的来源写一个 md，文件名：

```
YYYY-MM-DD_主题名_信源N_来源简称.md
```

例：`2026-06-22_字节跳动组织调整_信源1_36氪.md`

**信源 md 模板**（必须严格遵循）：

```markdown
---
date: YYYY-MM-DD
topic: 主题名
source: https://原文完整URL
source_title: 原文标题
source_author: 作者（如可知，否则留空或写"未知"）
source_date: 原文发布日期（如可知，否则留空）
tags: [标签1, 标签2, 标签3]
status: inbox
type: research-source
confidence: high   # high=多源互证 / medium=单源可靠 / low=观点或未经证实的传闻
synthesis: "[[YYYY-MM-DD_主题名_综述]]"
---

# 原文标题

## 核心要点

- 要点 1
- 要点 2
- 要点 3

## 原文摘要

（保留关键信息，去除广告、导航、页脚、评论区等噪音。客观陈述，不带评论。）

## 涉及实体

- 人：张三（角色）
- 组织：XX 部门
- 产品：XX

## 原文链接

- [原文标题](https://原文URL) — 作者/发布日期 — 抓取于 YYYY-MM-DD
```

### 第 8 步：写综合综述 md

每次调研**只写一篇**综合综述，文件名：

```
YYYY-MM-DD_主题名_综述.md
```

例：`2026-06-22_字节跳动组织调整_综述.md`

**综合 md 模板**（必须严格遵循）：

```markdown
---
date: YYYY-MM-DD
topic: 主题名
source: 多源综合（详见下文"来源"小节）
tags: [标签1, 标签2, 标签3, 标签4]
status: inbox
type: research-synthesis
search_rounds: 2
sources_count: 6
related:
  - "[[YYYY-MM-DD_主题名_信源1_来源简称]]"
  - "[[YYYY-MM-DD_主题名_信源2_来源简称]]"
  # ... 列出全部有效信源
---

# 主题名 · 调研综述

## 概览

（2-3 句话总览这次调研发现了什么，给读者一个最快速的锚点。）

## 关键发现

- 发现 1（来源：[[信源1文件名]]）
- 发现 2（来源：[[信源2文件名]]）
- 发现 3（来源：[[信源3文件名]]）
- ...

## 关键实体

- 实体 A（人/组织/产品）：角色或意义
- 实体 B：角色或意义

## 矛盾与分歧

- [[信源A]] 说 X，[[信源B]] 说 Y。更可信的是 X/Y，因为……
- 如无矛盾，写"本次调研未发现明显矛盾"。

## 悬而未决（Open Questions）

- 搜索未完全解答的问题 1
- 抓取失败/找不到来源的缺口（附 URL 和失败原因）
- 需要进一步研究的方向

## 来源

- [来源标题 1](https://URL1) — 作者 / 发布日期 — [[信源1文件名]]
- [来源标题 2](https://URL2) — 作者 / 发布日期 — [[信源2文件名]]
- ...

## 元信息

- 搜索深度：2 轮
- 信源数：N（其中有效 M，失败 K）
- 完成时间：YYYY-MM-DD HH:MM
- 抓取失败的来源（如有）：URL — 失败原因
```

### 第 9 步：报告用户

按以下格式简明汇报：

```
✓ 调研完成：{主题名}

目录：0_Inbox/搜索/YYYY-MM-DD/{主题名}/
综合：1 篇 | 信源：N 篇 | 搜索深度：2 轮

关键发现：
- 发现 1
- 发现 2
- 发现 3

悬而未决：K 条（详见综合页"Open Questions"）

下一步建议：
- 需要我帮你分类到 3_Resources/ 或 2_Areas/ 吗？（调用「知识分类」）
- 需要做关联扫描连到全库其他笔记吗？（调用「知识关联」）
```

## 来源偏好（置信度参考）

| 级别 | 来源类型 |
|------|---------|
| **高** | 官方公告/财报/官网新闻、权威媒体（如晚点、36氪、华尔街日报、路透、彭博）、官方文档 |
| **中** | 行业垂直媒体、知名博主的文章、维基百科 |
| **低** | 论坛帖（Reddit/V2EX/知乎匿名回答）、社交媒体贴、无来源的二手转述 |

**排除**：不作为高置信度来源——Reddit/论坛（仅作为指向一手来源的线索）、未注明日期的网页、自己不引证的文章。

## 安全护栏

### URL 校验（每次 WebFetch 前必做）

- ✅ 允许：`http://` `https://`
- ❌ 拒绝：`file:` `javascript:` `data:`
- ❌ 拒绝：内网地址 `10.x.x.x` / `172.16-31.x.x` / `192.168.x.x` / `localhost` / `127.0.0.1`
- ❌ 拒绝：搜索结果里没出现过的域名（防止被恶意重定向带偏）

### 写库前内容清洗

抓取的网页正文可能含恶意内容，写库前必须清洗：

1. **剥离标签**：去掉 `<script>` `<iframe>` `<style>` 标签及其内容
2. **转义 wikilink**：源正文里的 `[[` `]]` 转义为 `\[\[` `\]\]`，防止注入本库的双向链接图
3. **拒绝上游 frontmatter**：如果抓取的内容自己带 `---` YAML frontmatter，**丢弃它**——frontmatter 由本 skill 写，不由上游源决定
4. **截断**：单信源正文 ≤ ~50KB

### 失败处理

- 单个信源抓取失败：记录 URL + 原因到综合页 Open Questions，继续处理其他信源
- 全部失败：仍要写综合页（标注"本次调研未能抓到有效来源"+ 所有失败 URL 及原因），让用户知道发生了什么
- **绝不静默吞错**

## 与其他 skill 的协作

| 下游 skill | 衔接方式 |
|-----------|---------|
| **知识入库** | 网络调研产出的 md 已经是结构化的并落盘到 `0_Inbox/搜索/` 下，知识入库遇到带 `type: research-*` 的笔记时跳过、不重复处理 |
| **知识分类** | 通过 `type: research-synthesis` / `research-source` 字段识别搜索产物；综合页通常建议归入 `3_Resources/`（主题参考资料），信源页跟随综合页归类 |
| **知识关联** | 综合页的 `related` 字段已经建好了到所有信源页的 wiki 链接；关联扫描时会自动连到全库其他相关笔记 |

## 注意事项

1. **全程中文输出**（遵循 SOUL.md / CLAUDE.md），技术术语首次出现给中英对照
2. **frontmatter 的核心 4 字段**（date/source/tags/status）与现有 inbox 笔记完全一致，扩展字段（type/topic/confidence/synthesis/related）让下游 skill 能识别搜索产物
3. **文件名带日期前缀** `YYYY-MM-DD_主题名_...`（遵 CLAUDE.md 的硬规则）
4. **不依赖任何外部脚本**——只用内置的 `WebSearch` + `WebFetch` + `Write` + `Edit`。避开 Windows 上 bash/fcntl 跑不通的坑
5. **专注时效性信息**——本 skill 偏公司动态、新闻、组织变动等有时效性的主题；纯学术/深度多轮迭代研究不在本 skill 范围内
6. **PARA 不自动移动**——本 skill 只往 `0_Inbox/搜索/` 写，不主动把文件搬到 `1-4` 任何一级，搬移等用户确认（遵 CLAUDE.md）
7. **诚实标注不确定性**：找不到的来源、互相矛盾的说法，都明明白白写进综合页，不要"看起来很全"地糊过去
